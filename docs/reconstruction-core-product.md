# 暮らしの再建 Core Product Definition

制定日: 2026-08-12

## 1. プロダクトの役割

「暮らしの再建」は、令和8年熊本地震で被災した本人・家族・地域支援者が、制度知識がなくても、暮らしの困りごとから自治体等の公式情報と次に確認することへ進むための中立的な生活再建ナビである。

制度対象の判定、個別相談の受付、ケース管理、医療・法律・融資の判断、行政手続きの代行は行わない。

## 2. 対象利用者

- 被災した本人
- 本人と一緒に情報を探す家族
- 民生委員、地域役員、ボランティア、NPO等の地域支援者

利用者に制度名の知識を求めない。本人と支援者で制度データを分離せず、支援者向けの補足だけを補助導線として扱う。

## 3. CORE（必ず維持する機能）

COREは、これがないと「困りごとから正しい公式情報へ進む」という基本目的が成立しない機能である。

| ID | 機能 | 維持する理由 |
| --- | --- | --- |
| CORE-1 | 8つの困りごとカテゴリ | 制度名を知らない利用者の基本入口 |
| CORE-2 | 暮らし整理ナビ | 何から始めるか分からない利用者の入口 |
| CORE-3 | 自治体等の公式情報ナビ | どの一次情報を見るべきかを整理する、信頼性の中心 |
| CORE-4 | 自治体選択と `municipality` 引き継ぎ | 別自治体の情報混入を防ぎ、選び直しを減らす |
| CORE-5 | 個別情報0件・読込失敗時の公式fallback | 「情報なし」を「制度なし」と誤認させず、公式サイトへ必ず進める |
| CORE-6 | 公式情報検索 | 「水道」「税金」「家を直したい」等、知っている言葉から探す入口 |
| CORE-7 | アクションナビ（次に確認すること） | 公式情報を見ても次の行動が分からない状態を防ぐ |

アクションナビはCOREとする。ただし、診断・対象判定・大量のToDoにはせず、原則1画面2〜3件の確認事項に限定する。検索条件は検索語と自治体を基本とし、複雑な絞り込みは追加しない。

## 4. 固定する8カテゴリ

1. 住まい
2. お金・支払い
3. 証明・申請
4. 健康・介護
5. 子ども・家族
6. 仕事・事業
7. 農業・漁業
8. 暮らし・移動

新しい最上位カテゴリは原則追加しない。既存8カテゴリでは整理できない重大な利用者課題が実利用者テスト等で確認された場合に限り、例外として再検討する。

## 5. 主要3入口と基本利用フロー

主要入口の名称は次の3つに固定する。

1. **困りごとから探す**
2. **何から始めればいいか分からない**
3. **公式情報を言葉から探す**

```text
暮らしの再建
├─ 困りごとから探す
│  └─ 8カテゴリ
│     ├─ 次に確認すること
│     ├─ 自治体等の公式情報
│     └─ 関連カテゴリ
├─ 何から始めればいいか分からない
│  └─ 暮らし整理ナビ
│     └─ 気になる分野 → 公式情報
└─ 公式情報を言葉から探す
   └─ 検索語・自治体 → 公式情報

補助
├─ 支援者向け表示
├─ 確認メモ（相談メモ）
└─ 確認済み制度情報
```

基本フローは「トップ → 暮らしの再建 → 困りごと → 自治体 → 次に確認すること → 公式情報」。整理が必要な場合と検索語が分かる場合だけ、残る2入口を使う。確認メモは結果側、支援者向け表示は補助入口に置き、主要入口へ昇格させない。

## 6. SUPPORTING（補助機能）

| 機能 | 位置づけ |
| --- | --- |
| 確認メモ（相談メモ） | 本人・家族・地域支援者・公的窓口間で「何を確認したいか」を印刷・共有する。保存、履歴、担当者、状態、ケース番号、個人情報、クラウド共有は持たない |
| 支援者向け表示 | 本人と一緒に整理するための補足。専用ログイン、支援者DB、ケース管理を持たない |
| 関連カテゴリ | 複合する困りごとの見落としを減らす。制度該当の推薦として表示しない |
| 印刷 | 画面外で確認事項を共有するための補助 |
| 確認済み制度カード | 厳密に確認できた高需要・高リスク制度の付加価値。サービス成立の前提にしない |

確認済み制度情報を増やす場合は、利用頻度、判断ミスの影響、公式情報の理解しづらさ、契約前等の重大注意を優先する。全制度の収録は目標にしない。

## 7. OPTIONAL（利用実績により削除可能）

- 検索例
- 細かな関連カテゴリ
- 確認メモの手書き欄
- 補助的な折りたたみ説明

OPTIONALは主要フローを妨げず、保守負担や理解負担が効果を上回る場合は削除する。

## 8. REMOVE候補

- 役割が重複する入口、似たCTA
- 説明だけで遷移を増やす中間ページ
- 利用されない細かなフィルター
- `verificationStatus` 等の内部運用状態の利用者向け表示
- 死んだfixture導線、不要ページ、参照されない古いコード

今回、現行主要フローから削除した機能はない。すでに3入口へ整理済みであり、未完成機能の完成を目的化せず、必要性が実証されるまで保留する。

## 9. NOT_IN_SCOPE（原則実装しない）

- 個人アカウント、ログイン、CRM
- ケース管理、相談履歴、担当者、状態、ケース番号
- 個人情報DB、自由記述相談フォーム、クラウド共有
- 制度自動判定、AI制度判定、個人向け「おすすめ制度」
- AIチャット相談（現時点）
- 医療診断、法律判断、融資判断
- 行政申請代行、よか隊ネット熊本への相談受付システム
- GPS等の位置情報取得、プッシュ通知（現時点）
- 機微な困りごとの詳細な行動追跡・KPI化
- 全制度の網羅

## 10. 情報品質原則

- 自治体情報をすべて転載せず、「どの公式情報を見るべきか」を整理する。
- 制度条件、対象、期限、申請先の最終確認は `source` / `sourceLink` の一次情報へ委ねる。
- 個別情報が0件でも、自治体の災害関連公式情報または公式トップへのfallbackを出す。
- 「0件」を「制度・支援がない」と表現しない。
- `verification` は内部の品質管理に使い、内部状態を一般利用者へ露出しない。
- 公式情報の取得成功、誤分類、リンク切れ、古い情報、source変更、fallback、制度レビューを継続監視する。
- `sitePhase` で表示優先度は変えても、「暮らしの再建」の構造は変えない。

## 11. プライバシー・安全原則

- 困りごとや選択内容を保存・送信しない。
- 氏名、住所、病歴、所得、借入、家族関係等の入力を求めない。
- 困りごとの選択内容をAnalyticsへ送らない。
- 診断、適用判定、行政公式サービス、本人向け個別助言と誤認させない。
- JavaScript無効時にも市町村公式情報等へ進める代替導線を維持する。

## 12. 維持するデータ・技術基盤

- 自治体マスタ（21市町村）
- 公式情報収集と分類
- `official-nav`
- 固定8カテゴリの分類
- fallback
- `verification`
- `source` / `sourceLink`
- `nextAction`
- GitHub Actionsによる生成物・構文・回帰検証

必要性が生じない限り静的JSONと静的サイトを維持する。DB化、Next.js等への移行、大規模リライト自体を改善目標にしない。速く、壊れにくく、障害点が少ない構成を守る。

## 13. 新機能追加freeze

本定義の制定後、新機能追加を原則freezeする。「あると便利」は追加理由にしない。提案時はすべて次を確認する。

1. 被災者が公式情報へ進むために本当に必要か。
2. 既存機能で代替できないか。
3. 理解・操作を複雑にしないか。
4. 情報精度リスクを増やさないか。
5. 運用負担が増えすぎないか。
6. 個人情報を扱う必要が生じないか。

freeze解除は、次のいずれかを確認した場合に限る。

- 実利用者テストで重大な行き止まりが確認された。
- 行政等の情報提供方法が大きく変化した。
- 災害状況の変化により既存構造が機能しない。
- アクセシビリティ上の重大問題が確認された。

freeze中も、バグ修正、情報更新、リンク修正、実利用者テストに基づく最小UX改善は継続する。

## 14. 運用・改善方針

開発比率は「新機能開発: 低」「情報品質・運用: 高」「UX改善: 実利用者テストに基づく」とする。UX改善は、原則として「実利用者の観察 → 問題の記録 → 最小修正 → 再テスト」で進める。

PV、滞在時間、クリック数だけで価値を判断しない。次を主要なUX品質指標とする。

- 公式情報へ到達できる。
- 行政公式サービスと誤認しない。
- 本人が制度対象だと誤認しない。
- 行き止まりにならない。
- 主要導線をモバイル、キーボード、200%ズーム、印刷で利用できる。

技術的負債は、重複CSS・JS、不要ページ、古いコード、死んだfixture導線を小さな差分で整理する。安定コードを「きれいにする」ためだけの全面書き換えは禁止する。

## 15. 現在の最小完成形とリリース対象

本番で維持するリリース対象は、暮らしの再建トップ、固定8カテゴリ、暮らし整理ナビ、自治体公式情報ナビ、自治体選択引き継ぎ、fallback、公式情報検索、アクションナビ、関連カテゴリ、支援者向け補助、確認メモ、確認済み制度カード、印刷・no-JS導線、およびこれらを支える静的データ生成・検証フローである。

この構成を「安定した最小完成形」とする。次のステップは機能追加ではなく、公式情報の鮮度・分類・リンク・fallbackの運用監視と、A/B/C等の実利用者テストに基づく最小修正である。
