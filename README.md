# よか隊ネット熊本　災害・支援状況レポート

令和8年熊本地震（2026年7月28日 16:27 発生）の災害・支援情報をまとめたアーカイブ型の静的サイトです。「火の国会議」議事録を中核に、熊本県災害対策本部と各市町村の公式情報を、出典・確認時点とともに統合しています。本サイト自体は行政機関等が発信する一次情報ではありません。

次の2つの公的な一次資料を突き合わせて構造化しています。推測・按分は行いません。

| 一次資料 | 開催 | このサイトでの役割 |
|---|---|---|
| **火の国会議**（熊本県災害連携ネットワーク会議）の議事録 | 毎日18時 | 現場で何が起きて誰が動いているか。支援団体の報告、災害VCの状況、分野別の課題 |
| **熊本県 災害対策本部会議**の資料 | 1日2回（7:30・14:00） | 公式の集計。市町村ごとの避難・人的被害・住家被害・断水・給水所、罹災証明の日程 |

火の国会議が報告する県内合計は、その日14時時点の県災害対策本部会議の集計と一致します（避難者・避難所・住家被害・断水の全日で検算済み）。県の資料には**市町村ごとの内訳**があるため、会議記録だけでは「4市町の合計で44,380戸」としか言えなかった断水を、市町村別に出せるようになっています。

## 掲載方針

このサイトは緊急通報・安否確認の窓口ではありません。以下の原則で運用します。

1. **出典を必ず添える。** 数値・事実の各項目に、議事録の「回数 + ページ番号」を付けて原PDFへリンクする。
2. **議事録は要約だけにせず、構造ごと載せる。** 火の国会議の議事録は「今どこで何が起きていて、誰が何をしているか」を毎日更新している一次資料であり、要約だけでは失われる情報が多い。`meetings.html` では議事次第（県の報告 / 災害VC / 現地報告 / 分野別の課題 / シーズ / その他）をそのまま構造化して掲載する。
3. **議事録に書かれていないことは書かない。** 自治体別ページには、議事録内で自治体名が明記された事項のみを載せる。合計値からの按分はしない。
4. **定義の変化を隠さない。** 停電戸数 → 事故受付数、住家被害の「判定分」→「推定値」のように、県側の集計定義が途中で変わった箇所は注記で明示する。
5. **一次情報へ誘導する。** 制度・避難・罹災証明などの判断は、必ず国・県・市町村の公式発表を確認するよう各ページで案内する。

## 暮らしの再建が支援を取りこぼさないために

このサイトは制度そのものを掲載しません（`data/reconstruction/` は確認済みになるまで公開しない作りで、現在の公開制度は0件です）。実際に届けているのは**市町村の公式ページへの案内**なので、分類器が語を1つも当てられなかった記事は画面のどこにも出てきません。

そのため、`scripts/build-municipality-reconstruction-nav.mjs` の `keywords` に語を足すときは、次の順で確認してください。

1. `reports/municipality-official-navigation-quality.json` の `unclassifiedItems` を1件ずつ読む
2. 候補語が既存の分類済み記事に何を足すかを見る（広い語は誤分類を生みます。「窓口」を入れると、ペットの相談窓口まで証明・申請に混ざりました）
3. `scripts/test-reconstruction-coverage.mjs` の `MUST_CLASSIFY` に代表例を足す

ある分野の公式情報を1件も確認できなかったときは、行き止まりにせず次の3つを出します。

- 市町村の**災害情報ページ**（`config/municipality-disaster-hubs.json`。21市町村中20件を登録済みで、掲載前に1件ずつ開いて確認しました）
- その市町村で**情報がある分野**とその件数
- 分類の**確信度が低くて隠れている候補**（そうと分かる断り書きつき）

## 市町村の広報紙を扱うとき

`uto-bulletin.html` は宇土市発行「広報うと 災害臨時号vol.1」（2026年8月17日）の内容を並べ替えたページです。**紙面に書かれていないことは書きません。** 「詳細は決まり次第お知らせします」とある項目は、決まっていない項目としてそのまま示します（`bulletin-pending`）。

紙面はPDF内が画像で、テキストを抽出できません。PyMuPDFで高解像度に描画し、左右・上下に分割して読み取っています。読み取った内容は `data/reconstruction/uto-bulletin-vol1.json` に原文のまま置き、`scripts/test-uto-bulletin.mjs` がページとの**双方向の突き合わせ**をします。

- データにある電話番号・金額・期限がページから落ちていないか
- ページに**データに無い**電話番号・金額が混ざっていないか（勝手に足していないか）

市内表記の電話番号（例「（22）1111」）には市外局番0964を補っています。補う前に、宇土市公式サイトに掲載の代表番号 0964-22-1111 と紙面の表記が一致することを確認しました。

## お知らせの受け取り方（公式LINEなど）

市町村からのお知らせは公式LINEに移りつつあります。**LINEで配信された本文は、このサイトでは取得できません。** 配信は友だち登録した人のトーク画面にだけ届き、Messaging API はアカウントを運営する自治体自身のためのもので、第三者が読む口がないためです。公開のアカウントページ（`page.line.me/…`）にも配信本文は出ません（`/posts` は404）。

そのため `alert-channels.html` で配るのは**受け取り方だけ**です。データは `data/reconstruction/municipality-alert-channels.json`（手編集）で、手段ごとに出典URLと出典名を必ず持たせ、`node scripts/build-alert-channels.mjs` が出典なしのものを弾きます。追加するときは、**リンク先を実際に開いてアカウント名が一致することまで確認してください**（熊本市の公式SNS一覧に載っていたリンクの1つは、別事業者のアカウントに解決しました）。

確認できなかった市町村は空のまま「未確認」と表示します。手段が無いことにはしません。

この事実は集計ページの読み方にも効きます。自治体サイトの発信しか見ていないため、発信の少なさを対応の少なさと読ませないよう、`build-official-timeline` / `build-water-recovery` / `build-response-tracks` の `caveats` に「LINEに移っている場合がある」を入れています。根拠は、宇土市の防災行政無線の放送内容ページが発災前の2026年5月8日で更新が止まっていることです。

## 対象外にする公式ページ

市町村の公式ページを「暮らしの再建」の8分野へ自動で振り分けていますが、どの分野にも当てはまらないページがあります。災害対策本部会議の資料、広報紙、市の災害情報の入口ページ、市長メッセージ、報道機関向けの案内、他自治体への応援の連絡などです。これらを「取りこぼし」として数えていると、本当に見落としている支援が件数に埋もれ、毎日の自動更新も歯止めに引っかかって止まります。

そこで `config/reconstruction-out-of-scope.json` に、種類ごとの理由つきで「対象外」を定義しています。品質レポートでは `unclassifiedItems`（本当の取りこぼし）と `outOfScopeItems`（対象外・理由つき）に分かれます。

**これを抜け道にしないための約束**が3つあります。

1. 対象外の判定は、**分野を1つも当てられなかった記事にしか使いません**。分類できた記事を対象外で消すことはできない作りです。
2. 理由を必ず書きます（20字以上。テストで確認）。
3. どの記事にも当たらないルールは置けません。表題の書き方が変わってルールが空振りしていることに気づけなくなるためです（実際、全角括弧のまま書いて空振りしていました。`patterns` はNFKC正規化後の半角に対して書きます）。

さらに、収集した記事は「分類・対象外・未分類・除外」のどれか1つに必ず入り、合計が入力件数と一致することをテストで確認しています。どこかで記事が黙って消えていれば落ちます。

迷ったらルールに足さず、未分類のまま人が見る一覧に残してください。

## 市町村の災害対策本部会議

熊本市と八代市は、市が開く災害対策本部会議の資料を公開しています。火の国会議（支援団体の情報共有）とは別の会議で、市の側から見た避難所・住家被害・り災証明の数字が回ごとに載ります。これを回ごとに並べたのが [hq-kumamoto.html](hq-kumamoto.html) と [hq-yatsushiro.html](hq-yatsushiro.html) です。

対象は `config/municipality-hq-meetings.json` に書きます。市が資料ページを作ったらここへ足せば、取得もページも追随します。市によって載せ方が違うので `source` で切り替えます。

- `html` … 熊本市。一覧ページに会議ごとの本文が載っているので、そこから読みます。PDFは落としません。
- `pdf` … 八代市。一覧はPDFのリンクだけなので、資料PDFを取ってから「現在の状況等」のページを読みます。

```bash
node tools/fetch-municipality-hq.mjs && python3 tools/build-municipality-hq.py
```

資料PDFは1回20〜35MB・全体で1GBを超えるためリポジトリに入れません（`.gitignore` 済み）。取り出した文字だけを `sources/official/municipality-hq-text/` に残すので、PDFを取り直さなくてもページを作り直せます。取得側も、この文字がある回はダウンロードしません。市のサーバに同じファイルを何度も取りに行かないための約束です。

**数字の扱いで注意していること**。熊本市は第20回から「住家被害（届出をもとにした速報）」をやめ「住家被害認定調査実施件数」に変えました。8,897件から779件へ激減したように見えますが、数え方が違うだけです。別々の欄にして、ページ上でも「続きの数字として読まないでください」と出します。八代市は逆に、住家被害の総数2,500件を据え置いたまま内訳（全壊・一部損壊・分類未確定）だけが動きます。こうした気づきは書き置きにせず、表示のたびにデータから計算します（毎日増える会議に対して古くならないように）。

**行政の書き方を、市民の知りたいことから読めるようにしています**。資料は「支援団体等の状況」「被害の状況」といった行政の並びで書かれているので、`config/hq-reading-guide.json` で、資料のまとまりを暮らしのどの部分に関わるか（避難所／家の被害と証明／水・電気・ごみ・交通／支援と窓口／けが／市の動き）へ対応づけ、平たい説明を添えます。数字にも意味を添えます（り災証明の申請と交付の差＝待っている人の数）。

**横軸は「第何回」ではなく「発災からの日数」です**。会議の回を等間隔に並べると、1日に3回開かれた日（熊本市の発災2日目）も、2日空いた区間（8月15〜16日）も同じ幅になり、状況の動きが読めなくなります。図は日付で位置を決め、会議のあいだが空いた区間は破線にします。同じ日に複数回開かれた日は、その日の最後の回（＝その日の締めの数字）を使います。

時間軸で見るために3つの図を置いています。

- **主要指標の推移** … 避難者数、開いている避難所、り災証明の申請と交付（2本の線の開きが待っている人の数）、住家被害の内訳
- **会議の開かれ方** … 日ごとの開催回数。開かれなかった日は細い線で空けたままにします。開く回数そのものが、市の対応の段階を表します
- **話題の移り変わり** … どの話題がどの日に資料へ載っていたか。市の検討内容が時間とともにどう移ったかを見るための帯です

狭い画面では図を縮めず、箱ごと横に送れるようにしています（縮めると軸の文字が5px相当まで潰れて読めなくなるため）。

**日ごとに何が変わったか**は表示のたびに計算します。前の回から動いた数字を文にし、その回に初めて載った項目（対口支援、災害救助法、プッシュ型支援、防災ラジオの配布など）を並べます。行政が何をいつ始めたかが、ここで時間軸として読めます。項目名は数字や日付を外して比べるので、書き方が変わっただけの回は新項目になりません。

**言葉の説明は災害用語集と共有します**（`data/glossary-data.js`）。同じ言葉の説明が2か所にあると必ず食い違うので、terms.html と本部会議のページが同じデータを読みます。

`scripts/test-municipality-hq.mjs` が、出典が市のドメインであること・本文のない回に数字が入っていないこと・2つの数え方が同じ回に混在しないこと・**読み替えても資料の文が1文字も変わっていないこと**・**読み替えで資料の行が1行も落ちていないこと**・用語集と共有していること・自動更新に載っていること・メニューから辿れることを見ます。

## OGP（SNSやLINEに貼られたときの見え方）

`tools/build-seo.mjs` が全ページにOGタグを書き込みます。画像はページごとに割り当て、力を入れたページには専用の画像を作ります（共通画像だと貼られたときに中身が伝わりません）。

専用画像は `python3 tools/build-ogp-images.py` で作ります。絵は宇土市のページ（`uto-waste` / `uto-bulletin`）と同じ描き方（viewBox 120×82・線は共通の色・同じ配色）に揃えているので、画像を見てから開いても印象が食い違いません。文字はヒラギノを画像として焼き込みます（フォントを配布するわけではありません）。図に数字は入れません（読み手が実際の統計と取り違えないように）。

ページを増やすときは **3か所をそろえてください**。
1. `tools/build-ogp-images.py` の `PAGES` に追記して画像を生成
2. `tools/build-seo.mjs` の `specialImages` に割り当て
3. `node tools/build-seo.mjs` でタグを更新

`scripts/test-ogp.mjs` が、画像の実体があること・実寸が1200×630であること・宣言した寸法と実物が一致すること・`og:url` と `canonical` が食い違わないこと・専用画像を割り当てたページが共通画像に戻っていないこと・専用画像を使い回していないことを見ます。表題が長すぎるとイラストに重なるので、生成器は2行かつ列幅に収まるまで文字を小さくします。

## 導線の作り

メニューは2系統あります。実際に見えているのは `org-site.js` が組み立てるメガメニューで、HTMLに書いてある `<nav aria-label="メインメニュー">` は JavaScript 無効時にだけ見えるものです。**ページを増やしたら両方に足してください。** 片方だけだと「メニューから辿れないページ」ができます。

- 「令和8年熊本地震」…支援情報トップ／困りごと／避難所／自治体別／公的情報／支援する方／災害ボランティアセンター
- 「暮らしの再建」…8つの困りごとカテゴリ
- 「記録・資料」…**原資料をたどる**（日々の記録・議事録・市町村の公式発信・用語集）と、**発信から読み解く**（被災地の局面・水の復旧・5つの対応の流れ）

市町村の発信から読み解く3ページは同じ収集データを材料にした一組です。3ページ本体と入口となる3ページ（市町村の公式発信・自治体別・日々の記録）に、同じ並び順の `.reading-set` の帯を置き、3ページ側ではいま見ているページを抜いて示します。並び順・現在地・到達性は `scripts/test-site-navigation.mjs` で固定しています。

CSS・JSは `?v=` を付けて配信しています。中身を変えたら**必ず版を上げてください**（上げ忘れると利用者に古いものが出ます）。`styles.css` が `@import` で読むファイルは HTML 側の版では更新されないため、`@import url("...?v=…")` の側を上げます。

## 公式情報の定期更新

`.github/workflows/refresh-official-data.yml` が、3時間ごとに次の処理を自動実行します。GitHubの Actions 画面から `workflow_dispatch` で手動実行することもできます。

1. 熊本県災害対策本部会議の資料一覧と被害集計を取得
2. 対象21市町村の公式サイト・地震情報集約ページ・緊急情報を巡回
3. 災害VCを運営する市町村社会福祉協議会のサイトから募集・活動の発信を取得
4. 「防災情報くまもと」から開設中避難所を取得
5. 重複、日付、分類、PDF参照、県公式集計との整合性を検査
6. 検査に成功し、差分がある場合だけ `main` ブランチへ自動コミット

自動更新が編集するのは `data/generated/` と `sources/official/` 内の生成データだけです。火の国会議の原本PDF、議事録の構造化データ、手編集の要約は自動変更しません。避難所の取得原本は実行中の一時ファイルとして扱い、リポジトリにはサイト表示用の整理済みデータだけを反映します。

GitHub Actionsで書き込みエラーになる場合は、リポジトリの **Settings → Actions → General → Workflow permissions** を開き、`Read and write permissions` を有効にしてください。

ビルド・パッケージ依存はありません。リポジトリをそのまま静的ホスティングに置けば動作します。公開前のデータ検査スクリプトを同梱しています。ローカル確認は任意のHTTPサーバで。

```bash
python3 -m http.server 8000
```

公開前には、データ・PDF・ローカルリンク・県公式集計との整合をまとめて検査します。

```bash
node tools/check-data.mjs
node tools/build-shelters.mjs --check
```

どちらかがエラーになった場合は公開せず、表示された対象を原資料と照合してください。

## 日次更新の手順

### 1. 議事録PDFを追加する

その日の火の国会議PDFを `sources/hinokuni-meetings/` に置きます。ファイル名は `YYYYMMDD火の国会議NNN回.pdf` の形式に揃えてください。

> 既存の `sources/hinokuni-meetings/20260729火の国会議.pdf`（第492回）だけは、受領時のファイル名を保つため回数が入っていません。新規ファイルは必ず回数を含めてください。

### 2. `data/report-data.js` を更新する

`window.REPORT_DATA` の各配列に追記します。編集対象は主に以下です。

| キー | 内容 | 追記のタイミング |
|---|---|---|
| `days[]` | 会議日ごとの統計・見出し・要約・アクション・注記 | 毎回（1日1件） |
| `municipalEvents[]` | 自治体名が明記された事項 | 該当があれば |
| `supportEvents[]` | 支援分野に紐づく活動・ニーズ | 該当があれば |
| `metrics[]` | グラフに出す指標の定義 | 指標を増減するときだけ |

`days[]` 1件の形:

```js
{
  date: "2026-08-04", meeting: 498, disasterDay: 8, attendees: 180,
  pdf: "sources/hinokuni-meetings/20260804火の国会議498回.pdf",
  areas: ["宇土市", "宇城市"],          // 議事録で言及された自治体
  stats: {
    injured: 161, deaths: 38,           // 人的被害
    evacuees: 7646, shelters: 146,      // 避難
    outages: null,                      // 数値がない日は null
    outageStatus: "おおむね解消",        // null のとき代わりに出す文言
    homes: 13393, waterOutages: 44380,
    waterOutageAreas: ["宇城市", "甲佐町", "八代市", "氷川町"]  // 断水戸数の内訳自治体
  },
  topics: ["被害", "避難"],              // timeline.html の絞り込みに使う
  headline: "...", summary: "...",
  actions: ["...", "..."],
  note: "..."                           // 数値の定義・留保はここに書く
}
```

**数値を入れるときの注意**

- 議事録に載っていない指標は `null` にします。`0` は「実際に0だった」を意味するので使い分けてください（例: 8月4日の停電は「おおむね解消」であって0件ではないため `outages: null` + `outageStatus`）。
- `waterOutageAreas` は断水戸数がどの自治体の合計かを示します。トップの断水カードの説明文（「宇城・甲佐・八代・氷川の4市町合計」）はこの配列から自動生成されます。**書き忘れると「会議資料に記載された県内の合計」という断定を避けた文言に切り替わります。** 数値だけ更新して範囲の説明が古いまま残る事故を防ぐための仕組みです。
- 集計定義が前日と変わったら、必ず `note` に書きます。グラフは同じ線で繋がってしまうため、注記がないと読み手が誤読します。
- `municipalEvents[]` / `supportEvents[]` には `page` を必ず入れます。PDFの該当ページに直接リンクするために使います。

### 3. `data/minutes-data.js` を更新する

議事録の中身そのものを載せるファイルです。`data/report-data.js` が「数値と要約」なのに対し、こちらは**議事次第の構造をそのまま**持ちます。`meetings[]` の末尾に1件追記します。

```js
{
  meeting: 498, date: "2026-08-04", disasterDay: 8, series: 7, pages: 13,
  pdf: "sources/hinokuni-meetings/20260804火の国会議498回.pdf",
  venue: "くまもと災害ボランティア団体ネットワーク（KVOAD）事務局",
  attendance: { onsite: 25, online: null, total: null },   // 記載がない欄は null
  orgs: ["熊本県社協", "ソナエトコ", …],                    // 【参加団体】をそのまま
  sections: [ … ]
}
```

`series` は表紙の「令和8年熊本地震 第◯回」、`meeting` は「第◯回 火の国会議」です。両方あるので取り違えに注意してください。

**sections[] の書き方**

`key` は `sectionDefs` のいずれか（`pref` 県の報告 / `vc` 災害VC / `field` 現地報告 / `needs` 被災者の課題 / `seeds` シーズ / `other` その他）。その回に無い議題は書かなくて構いません。

```js
{
  key: "pref", page: 2,
  groups: [
    {
      title: "被害状況等", page: 2, source: "第14回災害対策本部会議より",
      items: [
        { label: "人的被害", text: "161人（うち死亡38名）…" },   // 項目名つきの数値・制度
        { speaker: "熊本DWAT", text: "段ボールベッドの整備が…" }, // 団体の発言
        { text: "避難生活の環境改善が必要。" },                    // 発言者が特定されない共有事項
        { text: "…", link: { label: "日本財団 助成", url: "https://…" } }
      ]
    }
  ]
}
```

- **`page` は必ず入れます。** 各グループ見出しの右に「p.4 ↗」が出て、原本PDFの該当ページを直接開きます。ここが議事録ビューアの生命線です。
- 「4、被災者の状況と課題」の各小見出しには `theme` を付けます（`home` 在宅 / `shelter` 避難所 / `car` 車中泊 / `food` 食と栄養 / `children` 子ども / `supplies` 物資 / `welfare` 保健医療福祉・要配慮者 / `foreign` 外国人 / `pets` ペット・飼い主 / `house` 家屋保全）。**これを付け忘れると、その項目は分野フィルタに出てきません。** 分野を選ぶと全回を縦断して表示する仕組みなので、付け忘れは「その日の課題が無かったこと」になってしまいます。
- 「2、災害ボラセン設置状況」の市町村一覧は `groups` ではなく `vcTable` に書きます。表として描画され、開所日・活動開始日の変化を回ごとに追えます。

```js
{
  key: "vc", page: 3,
  vcTable: {
    page: 4, total: 11, heading: "災害VC 設置状況（11か所）",
    rows: [
      { name: "熊本市", status: "8/3開所・8/4活動開始", detail: "熊本市社協本所（新町）。一般ボラ募集は8/5から開始。" }
    ],
    normal: { label: "通常VCとして活動見込み", names: ["上天草市", "大津町"] },
    note: "…"        // 任意
  },
  groups: [ … ]      // 表に入らない県社協からの共有事項はこちら
}
```

**要約するときの原則**

語順や表記は読みやすく整えてかまいませんが、**数値・団体名・日付・固有名詞は原本のまま**にします。議事録に無い補足（他資料での裏取り、推測、按分）は入れません。発言者が「K)」「県）」のように略記されている箇所は、文脈から確実に分かる場合のみ `KVOAD` `熊本県` と展開します。分からなければ略記のまま残してください。

### 4. 県災害対策本部会議のデータを更新する

[令和8年熊本地震に係る災害対策本部会議](https://www.pref.kumamoto.jp/soshiki/222/274487.html) に、会議ごとの資料が掲載されます。2コマンドで取り込みます。

```bash
node tools/fetch-hq.mjs
```

県の掲載ページから資料PDFを取得し、カタログ（`sources/official/hq-index.json` と `data/generated/hq-index.js`）を書き出します。取得済みのPDFは再取得しません。

```bash
python3 tools/build-hq-damage.py
```

「人的被害等の状況」PDFの表を読み、`data/generated/hq-damage-data.js` / `data/generated/hq-latest.js` と、抽出結果の保存（`sources/official/hq-damage/*.json`）を生成します。

**PDF本体はコミットしません。** 全82件で約84MBあるためです。県の添付ファイルURLは安定しているので、サイトからは県のURLへ直接リンクしています。抽出結果のJSONはコミットするので、PDFが手元になくても中身は追えます。

**依存**: `build-hq-damage.py` だけ PyMuPDF が必要です（`pip install pymupdf`）。サイト本体と他のツールに依存パッケージはありません。

**列構成が毎回変わります。** 停電列は途中で消え、住家被害は1列 →（一部破損なしの）内訳 → 内訳＋計、と変化します。「一部破損」と「一部損壊」、「軽傷」と「軽症」のように表記も揺れます。そのため列番号ではなくヘッダーの見出しから対応づけています。**新しい見出しが出てきた場合は取りこぼすので、下の検算で気づけるようにしています。**

```
・2026-07-29 07:30: injuredMinor、injuredSevere は「不明」表記のセルがあるため検算を省略
スナップショット 13件（2026-07-29 07:30 〜 2026-08-05 14:00）
  検算OK（各列の内訳合計と資料の合計行が一致）
```

- **「検算OK」が出なかったら、その回のデータを使ってはいけません。** 各列について「45市町村＋市町村に割り当てられない行（身元不明・災害との関連調査中など）の合計」が資料の合計行と一致するかを見ています。一致しないのは、たいてい新しい列見出しを取りこぼしたときです。
- 「不明」のように数値でないセルは注記として保存し、その列の検算は省略します（7月29日の重症「不明（２名）」など）。
- 罹災証明・住家被害認定調査の日程は、資料の2ページ目に載っている回だけです。最後に載っていた回のものを使い、サイト上でも「◯月◯日時点の資料より」と明示します。

### 5. 避難所データを更新する

[防災情報くまもと](https://portal.bousai.pref.kumamoto.jp/?p=evacuation/shelter) の避難所JSONを取得して保存し、生成スクリプトを実行します。

```bash
curl -sS "https://portal.bousai.pref.kumamoto.jp/data/shelter/shelter.json" \
  -o "sources/official/kumamoto-open-shelters-$(date +%Y%m%d-%H%M).json"
```

```bash
node tools/build-shelters.mjs
```

引数なしで実行すると `sources/official/` 内で最も新しい `kumamoto-open-shelters-*.json` を選び、`data/generated/shelters-data.js` を上書きします。ファイルを明示することもできます。

```bash
node tools/build-shelters.mjs sources/official/kumamoto-open-shelters-20260805-1156.json
```

**抽出条件**（スクリプト内で完結）

- `shelterStartTimestamp` があり、`shelterEndTimestamp` が空欄 = 開設中
- かつ `data/report-data.js` の `municipalities[]` に載っている21市町村のもの

取得時刻はファイル名の `YYYYMMDD-HHMM` から読み取り、`metadata.retrievedAt` としてサイト上に「取得 ◯月◯日 ◯時◯分」と表示されます。**ファイル名の時刻は取得した実時刻にしてください。** 秒まで指定したい場合は `--retrieved-at=2026-08-05T11:56:22+09:00` を渡します（表示は分までなので通常は不要）。

書き込まずに差分の有無だけ見るには `--check` を付けます（差分ありで終了コード1）。

```bash
node tools/build-shelters.mjs --check
```

補足IDの誤り、緯度経度の欠損、開設中0件などはスクリプトが警告・中断します。`data/generated/shelters-data.js` は生成物なので、直接編集しても次回の生成で消えます。

### 6. 避難所への会議補足を足す（任意）

議事録に施設名が明記された報告があれば、`data/shelter-supplements.json` に追記します。県の施設ID（`facilityId`）をキーにします。

```json
{
  "00002252": [
    {
      "date": "2026-08-01", "meeting": 495, "page": 12,
      "pdf": "sources/hinokuni-meetings/20260801火の国会議495回.pdf",
      "text": "避難中の猫4匹について、飼い主が片付けに行く間の預かり支援ニーズを報告。"
    }
  ]
}
```

施設IDは生成済みの `data/generated/shelters-data.js` を施設名で検索すると分かります。存在しないIDを書いた場合は生成時に警告が出ます。

## SNS シェア用画像（OGP）

`ogp.png`（1200×630）を全ページの `og:image` に指定しています。差し替えるときは同じ寸法で `ogp.png` を置き換えてください。

`og:image` と `og:url` は**相対指定**にしてあります。公開ドメインが確定していないためで、主要なクローラは取得したページのURLを基準に解決します。カスタムドメインを設定した場合は、絶対URLに書き換えるとサムネイルの取得がより確実になります。

```html
<meta property="og:url" content="https://example.jp/index.html">
<meta property="og:image" content="https://example.jp/ogp.png">
```

favicon は `favicon.png`（32px）と `apple-touch-icon.png`（180px）です。

## 既知の制約と運用上の注意

- **JavaScript が必要です。** 統計・一覧・地図はすべてクライアント側で描画します。JS が無効な環境では各ページの `noscript` から公式サイトへ誘導する構成になっています。
- **`data/report-data.js` に構文エラーがあると全ページのJSが止まります。** 更新後は必ずブラウザのコンソールを確認してください（`app.js` は読み込み失敗時にページ上部へ警告を出します）。`data/minutes-data.js` の構文エラーは議事録ビューアだけを止め、他ページには波及しません（`minutes.js` が独立して try で囲んでいます）。文法チェックだけなら次のコマンドでできます。

```bash
node -e "global.window={};require('./data/minutes-data.js');console.log(window.MINUTES_DATA.meetings.length+'回')"
```

- **避難所データは取得時点のスナップショットです。** 開設状況は随時変わるため、サイト上でも「支援活動前に再確認」を明示しています。
- **`index.html` の「開設中◯件」と会議資料の「避難所◯か所」は一致しません。** 出所（県の施設データ / 会議報告）と時点が異なるためで、それぞれ別の数値として扱っています。
- **県資料の集計定義は途中で変わります。** 停電は「戸数」→「事故受付数」→ 列そのものが消滅、住家被害は「判定分」→「推定値」と変化しています。グラフや推移は同じ線でつながってしまうため、`data/report-data.js` の `note` と各ページの注記で明示しています。値が取れない時点はサイト上でも線を切って、0 と区別しています。
- **県資料PDFはリポジトリに入れていません。** 県の公開ページが変わるとリンク切れになります。抽出結果は `sources/official/hq-damage/` に残るので数値は追えますが、原本の保全が必要になった場合は取得方針の見直しが要ります。
- **議事録PDFの容量。** 1日あたり約800KB がリポジトリ履歴に積み上がります（2026年8月時点で計5.7MB）。長期運用する場合は Git LFS への移行、または別ストレージへの退避を検討してください。公開済みURLが変わる作業なので、移行時はリダイレクトの用意が必要です。
